# 图存储选型记录（GraphRAG 存储层）

> **状态**：已决策（供后期优化参考） | **关联**：[ROADMAP.md WP7](../ROADMAP.md)
>
> **决策**：WP7 GraphRAG 采用 **MySQL 邻接表 + JGraphT 内存子图**，通过 `GraphPort` 接口封装实现，升级路径预留 TuGraph 单机。
>
> **决策日期**：2026-09-15

---

## 1. 前提：图是派生物，不是源数据

本项目的知识图谱（实体/关系）全部由 LLM 从 chunk 抽取而来，**可随时从 MySQL 中的 chunk 重建**。图在本系统中是检索的辅助索引，不是核心业务数据。这一定位是整个选型的出发点——凡是只对"图是一等公民"场景成立的优点，在这里都不兑现。

## 2. 候选方案全景（按重量级四档）

### 档位一：关系库存图（当前选择）

MySQL 两张表 `kg_entity` / `kg_edge`，1-2 跳查询靠 JOIN；复杂遍历与图算法用 JGraphT 加载 KB 子图到内存完成。

- 注意：**MySQL 8.0 才有递归 CTE**，5.7 上变长路径只能应用侧循环展开。当前限 1-2 跳，自 JOIN 够用；建议 v2.2 前将部署基线升到 MySQL 8.0（5.7 已 EOL）。
- 增强变体即最终形态：**MySQL 持久化 + JGraphT 内存遍历/算法**（PageRank、社区发现、连通分量等上百个现成算法，纯 Java）。

### 档位二：嵌入式/进程内图引擎（本轮否决）

TinkerPop/TinkerGraph（Apache 2.0，Gremlin 遍历、进程内常驻）；Neo4j Embedded（许可已收紧，实际出局）。部署上仍是单 Jar，但见 §3 对比，收益不匹配场景。

### 档位三：独立图数据库（升级路径）

| 产品 | 协议 | 评估结论 |
|------|------|----------|
| **TuGraph**（蚂蚁） | Apache 2.0 | **唯一推荐升级目标**：单机版轻量、Java SDK、可离线安装、商业分发无许可顾虑 |
| Neo4j | GPLv3（社区） | 生态最好、自带向量索引；独立进程部署许可无碍，集群需商业授权。备选 |
| NebulaGraph | Apache 2.0 | 十亿级边分布式设计，需 3 类组件集群，中小企业规模是负资产 |
| Memgraph | BSL | 内存优先、流式强；许可需合规评估 |
| FalkorDB | SSPL | Redis 模块形态可搭现有 Redis，但破坏 Redis 纯净运维 + SSPL 合规成本 |
| JanusGraph | Apache 2.0 | 依赖 HBase/Cassandra + ES，过重，不适用 |
| ArangoDB | BSL | 多模型卖点与现有架构（文档在 MySQL）不互补 |

### 档位四：云服务（直接排除）

阿里云图数据库 GDB 等，与私有化/不出域定位冲突。

> RDF 三元组库（Jena/GraphDB）是另一条技术路线，适合本体推理/SPARQL 场景；GraphRAG 应采用 LPG 属性图模型，不在候选之列。

## 3. 核心对比：嵌入式图引擎 vs MySQL + JGraphT

| 维度 | 嵌入式图引擎 | MySQL + JGraphT ✅ |
|------|---------------------------------------------|------------------|
| 部署形态 | 图引擎活在 JVM 内，数据落本地文件，仍是单 Jar | MySQL 现有组件 + 纯 Java 库，零新增 |
| 数据一致性 | 图文件与 MySQL **跨存储**，chunk 删除需补偿逻辑或容忍窗口期孤儿边 | 同一事务边界：删文档/chunk/边一个事务，外键兜底 |
| 持久化价值 | 图可重建，引擎自有格式（Gryo/GraphML）的持久化收益打折，反而多一套备份对象 | 图就是 MySQL 表，现有 backup-all.sh 顺带覆盖 |
| 运维透明度 | 二进制格式，SQL 不可查不可修，排障要写代码 | SQL 直接可查可修；管理界面（实体/冲突/缺口）开发成本低 |
| 查询能力 | Gremlin 变长路径/模式匹配是本行 | 1-2 跳 SQL JOIN / Java 循环足够；变长遍历需自己写 |
| 图算法 | TinkerPop 进程内算法有限 | JGraphT 反而更强（百个现成算法） |
| 内存模型 | 整图常驻堆内，与 Lucene/ONNX 抢内存，多 KB 下线性涨 | 按 KB 懒加载子图（数千边=毫秒级），可缓存可淘汰 |
| 并发/多实例 | 进程内私有状态，多实例各自副本 | 表天然共享，JGraphT 视图是可丢弃缓存 |
| 许可 | TinkerGraph Apache 2.0；Neo4j Embedded 实际出局 | JGraphT 双许可（EPL-2.0 / LGPL-2.1），依赖使用无传染 |
| 团队心智 | 需学 Gremlin 新范式 | SQL + Java 集合操作，零学习成本 |
| 迁移路径 | 嵌入式文件迁独立图库需专门 ETL | MySQL 即源，换 TuGraph 重放抽取管道，换 GraphPort 适配器 |

**本质区别**：嵌入式图引擎的卖点（索引无关邻接、深度遍历、图原生持久化）只在"图是一等公民"前提下兑现——图是核心数据、遍历是主访问模式、路径查询复杂。本项目图是**可重建的辅助索引**，浅查询 + 生命周期与文档严格同步 + 运营要能直接看数据，全部指向 MySQL + JGraphT。

## 4. 切换信号（出现任一条即重新评估）

1. 图查询成为主路径：用户直接"查图"而非"检索文档"，出现复杂路径模式需求
2. 在线增量维护的大图（单 KB 边数 >50 万）+ 高频图算法，懒加载延迟不可接受
3. JOIN 查询 P95 >200ms 且无法用索引/限跳数优化
4. 图需要脱离知识库独立成为共享服务（多应用访问）

## 5. 升级路径

```
当前：MySQL 8.0 邻接表 + JGraphT 内存子图（GraphPort 接口封装）
  │  §4 任一信号触发
  ▼
TuGraph 单机（Apache 2.0，离线包可达，Java SDK）
  │  仅当分布式多租户规模
  ▼
NebulaGraph
```

切换成本控制：抽取管道产物（实体/关系 JSON）落 OSS 归档，重放即完成向新存储的 ETL；`GraphPort` 只暴露 `linkEntities / neighbors / upsertGraph / deleteByDoc` 四类操作，适配器工作量约 1 人周。

## 6. 不引入的东西

- 独立图数据库（未触发 §4 信号前）
- RDF 三元组栈
- 嵌入式图引擎（本轮否决，TinkerGraph 常驻堆内存与跨存储一致性是主因）
